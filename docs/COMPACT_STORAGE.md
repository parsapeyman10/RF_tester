# ذخیره‌سازی فشرده (RFC v2) و ظرفیت «نصف فلش»

## ۱) فرمت جدید چیست؟ (نسخه ۲ — حفظ کامل زمان)

پیش از این هر رکورد یک فایل جداگانه `.dat` به اندازهٔ **۲۵ بایت** بود؛
روی FAT عملاً هر فایل **یک کلاستر (~۵۱۲ بایت)** می‌گرفت
یعنی ≈ **۵۱۲ بایت واقعی به‌ازای هر ۲۵ بایت داده** (بیش از ۹۵٪ هدررفت).

### RFC v2 (تولید فعلی) — هر رکورد **۶ بایت**

| فیلد | بیت | مقدار |
|---|---:|---|
| `sod` | 17 | **ثانیهٔ روز از RTC (0..86399)** — لحظه‌ای، بدون زنجیره/انباشت |
| `temp` | 8 | **دما صحیح °C** (بدون اعشار، int8) |
| `hum` | 7 | **رطوبت صحیح %** (بدون اعشار، 0..100) |
| `nbcm` | 4 | وضعیت NBCM1..4 (بیت به بیت — زمان سوییچ با همین ثبت می‌شود) |
| `dnum` | 8 | اختلاف شماره سیکل NUM |
| `rsvd` | 4 | رزرو |
| **جمع** | **48** | **= 6 بایت** |

- **تاریخ (Y/M/D):** در هدر فایل روز + نام فایل (دو نسخه)
- **ساعت/دقیقه/ثانیه:** هر رکورد ثانیهٔ خودش را **مستقل** از RTC می‌گیرد  
  → **هیچ خطای انباشت زمانی وجود ندارد؛ زمان سوییچ و خوانش دقیق است**
- هدر ۲۰ بایت فقط یک‌بار در ابتدای روز
- v1 (رکورد ۸ بایتی قدیمی) همچنان قابل خواندن است

**حجم مؤثر: ≈ ۶ بایت + ۲۰/۷۲۰ ≈ ۶٫۰۳ بایت به‌ازای هر رکورد**

---

## ۲) فرمول ظرفیت

```
تعداد رکورد = حجم فضای ذخیره‌سازی ÷ 6
ساعت پایش  = (حجم ÷ 6) ÷ (3600 ÷ interval_second)
```

با **اینتروال فعلی = ۱۲۰ ثانیه** (هر ۲ دقیقه یک رکورد):

```
ساعت پایش = حجم_بایت ÷ (6 × 30) = حجم_بایت ÷ 180
```

> «نصف حافظه فلش» = `حجم_کل_فلش / 2`

## ۳) جدول پاسخ — با RFC v2 (۶ بایت)

### فرض: هر ۱۲۰ ثانیه یک رکورد (کد فعلی)

| فلش کلی ESP32 | نصف فلش (فضای داده) | ساعت پایش | تقریباً به روز |
|---|---:|---:|---:|
| **۴ MB** (WROOM معمولی) | ۲٬۰۹۷٬۱۵۲ B | **≈ ۱۱٬۶۵۰ ساعت** | **≈ ۴۸۵ روز** |
| **۸ MB** | ۴٬۱۹۴٬۳۰۴ B | ≈ ۲۳٬۳۰۱ ساعت | ≈ ۹۷۱ روز |
| **۱۶ MB** | ۸٬۳۸۸٬۶۰۸ B | ≈ ۴۶٬۶۰۳ ساعت | ≈ ۱٬۹۴۲ روز |

### مقایسه با فرمت قدیم (یک فایل به‌ازای هر رکورد + سربار FAT)

| سناریو | نصف فلش ۴MB | ساعت پایش (۱۲۰s) |
|---|---:|---:|
| قدیم — با سربار واقعی FAT (~۵۱۲B/فایل) | ۲٬۰۹۷٬۱۵۲ | **≈ ۱۳۶ ساعت (~۶ روز)** |
| **جدید RFC v2 (۶ بایت، فایل روزانه)** | ۲٬۰۹۷٬۱۵۲ | **≈ ۱۱٬۶۵۰ ساعت (~۴۸۵ روز)** |

یعنی با همان نصف فلش، حدود **۸۵ برابر** فرمت قدیمِ عملی پایش دارید.

## ۴) اگر اینتروال عوض شود (روی نصف فلش ۴MB)

| اینتروال | ساعت پایش RFC v2 | روز |
|---|---:|---:|
| ۶۰ ثانیه | ≈ ۵٬۸۲۵ | ≈ ۲۴۳ |
| **۱۲۰ ثانیه (فعلی)** | **≈ ۱۱٬۶۵۰** | **≈ ۴۸۵** |
| ۳۰۰ ثانیه | ≈ ۲۹٬۱۲۷ | ≈ ۱٬۲۱۴ |
| ۱ ثانیه | ≈ ۹۷ | ≈ ۴ |

```text
ساعت = فضای_بایت / 6 / (3600 / interval_s)
```

## ۵) تضمین «هیچ دیتایی گم نمی‌شود»

| داده | وضعیت |
|---|---|
| **زمان/تاریخ** | ثانیهٔ روز لحظه‌ای RTC در هر رکورد (نه جمع زنجیره‌ای) + تاریخ در هدر/نام فایل |
| **دما** | صحیح درجهٔ سانتی‌گراد (بدون اعشار — طبق درخواست) |
| **رطوبت** | صحیح درصد ۰..۱۰۰ (بدون اعشار) |
| **سوییچ NBCM1/2** | ۴ بیت وضعیت در همان رکوردِ زمان‌دار |
| **NUM سیکل** | از هدر + dnum (در سیکل عادی همیشه ۱) |
| **فایل‌های v1 قدیمی** | همچنان خوانده/آپلود می‌شوند |

## ۶) پیاده‌سازی در کد

| فایل | تغییر |
|---|---|
| `esp32_controller_FIXED/*.ino` | نوشتن v2 (۶ بایت)، خواندن v1+v2، آپلود چندرکوردی، بازیابی NUM بعد از ریست |
| `app.py` | پارسر v1+v2 در `parse_rfc_bytes` + آپلود پوشه‌ای `.rfc` |
| اپ اندروید | پنل **دو NBCM** (N3/N4 از UI حذف — در داده برای سازگاری می‌ماند) |
| وب‌اپ | قبلاً فقط NBCM1/2 نمایش می‌داد |

## ۷) نکته دربارهٔ «نصف حافظه فلش»

- منظور **فلش داخلی ESP32** باشد: جدول بالا (معمولاً ۴MB).
- منظور **کارت SD** باشد: هر گیگابایت با v2 ≈ `1e9/6/30 ≈ 5,555 ساعت ≈ ۲۳۱ روز` (هر ۱۲۰ ثانیه).
- برای استفاده از نصف فلش داخلی به‌عنوان فضای داده، پارتیشن LittleFS باید ~۵۰٪ تعریف شود (مدل ماژول را بگویید تا جدول پارتیشن بسازم).
