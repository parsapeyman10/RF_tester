# فریمور ESP32 نسخه‌ی ۲.۰ — فرایند جدید

## ۱) چرخه‌ی کاری (هر ۲ دقیقه)

```
        ┌──────────────── سیکل ────────────────┐
        │                                      │
  رله ۱ تریگ ──► پنجره‌ی شنود فیدبک BCM1 ──► OK/NOK ثبت شد
        │        (تا ۳ تلاش + چکش‌کاری)         │
        ▼
  رله ۲ تریگ ──► پنجره‌ی شنود فیدبک BCM2 ──► OK/NOK ثبت شد
        │        (تا ۳ تلاش + چکش‌کاری)         │
        ▼
  خواندن SHT31 (۱۰ نمونه، میانگین + فیلتر پرش)
        ▼
  خواندن تاریخ/ساعت از RTC
        ▼
  یک رکورد: NUM, NBCM1, NBCM2, Temp, Hum, Date, Time
        ▼
  ذخیره روی SD  ──►  آپلود به ESP8266 ──► گرفتن «OK» ──► حذف فایل
```

نکته‌ی کلیدی نسبت به نسخه‌ی قبل: **رله‌ها دیگر با هم و به‌صورت یک «سیکل درب» زده نمی‌شوند.**
ترتیب کاملاً سریالی است — تا کار رله ۱ و داوری BCM1 تمام نشود، سراغ رله ۲ نمی‌رود.

### نگاشت رله ↔ BCM (قابل تغییر در یک خط)

```cpp
const ChannelConfig CHANNELS[] = {
  { "BCM1", 2, 13, 15 },   // رله پین 2  -> فیدبک Open=13 , Close=15
  { "BCM2", 4, 16, 17 },   // رله پین 4  -> فیدبک Open=16 , Close=17
};
```

چون سؤال نگاشت بی‌پاسخ ماند، فرض پیش‌فرض این است که **هر رله متعلق به یک دستگاه است**.
اگر در سخت‌افزار شما رله ۱ = فرمان Open برای هر دو دستگاه و رله ۲ = فرمان Close است،
فقط همین جدول را به این شکل عوض کنید:

```cpp
const ChannelConfig CHANNELS[] = {
  { "OPEN",  2, 13, 16 },  // فرمان Open ، فیدبک Open دو دستگاه
  { "CLOSE", 4, 15, 17 },  // فرمان Close، فیدبک Close دو دستگاه
};
```

### داوری موفقیت

| پارامتر | پیش‌فرض | معنی |
|---|---|---|
| `REQUIRE_BOTH_FEEDBACKS` | `true` | موفقیت = دیدن هر دو فیدبک Open و Close آن کانال |
| `RELAY_PULSE_MS` | 800 | مدت تریگ رله |
| `FEEDBACK_WINDOW_MS` | 3000 | مهلت پاسخ BCM بعد از تریگ |
| `RELAY_MAX_ATTEMPTS` | 3 | تعداد تلاش هر رله |
| `ENABLE_HAMMERING` | `true` | اگر نیمه‌کاره ماند، ۵ ضربه‌ی ۵۰ms و بررسی دوباره |
| `PULSE_CONFIRM_MS` | 100 | حداقل مدت HIGH تا پالس معتبر شمرده شود |
| `CYCLE_PERIOD_MS` | 120000 | فاصله‌ی سیکل‌ها |

## ۲) ذخیره‌سازی (به‌روزشده در V2.1)

ذخیره‌سازی روی SD از «یک فایل برای هر رکورد» به **«یک فایل در روز + آفست آپلود»**
تغییر کرد. جزئیات کامل و دلیلش در [`DATABASE_METHOD.md`](DATABASE_METHOD.md).

### قدیمی

هر رکورد شامل **شماره، وضعیت BCM ها، دما، رطوبت، تاریخ و ساعت** است و
ساختار باینری‌اش دست‌نخورده مانده (۲۵ بایت، `<iff????iBBBBB`) تا:

- پارسر `sscanf` سمت ESP8266،
- `parse_industrial_line` در `app.py`،
- و آپلود دستی فایل‌های `.dat` در صفحه‌ی `/upload_dat`

همگی بدون تغییر کار کنند. تست `.github/scripts/test_protocol.py` همین را قفل کرده است.

## ۳) گرفتن خودکار تاریخ و ساعت در بوت

سه مرحله، به ترتیب اولویت:

1. **NTP از طریق مودم / هات‌اسپات گوشی**
   لیست شبکه‌ها را اینجا پر کنید:
   ```cpp
   const WifiCred TIME_NETWORKS[] = {
     { "MyModem",       "modem-password" },
     { "iPhone-Peyman", "12345678"       },
   };
   ```
   منطقه‌ی زمانی روی تهران تنظیم شده: `const char *TIMEZONE_TZ = "<+0330>-3:30";`

2. **ساعتِ خودِ گوشی، بدون اینترنت**
   اگر NTP نشد، دستگاه هات‌اسپات **`SetClock`** (پسورد `12345678`) را بالا می‌آورد.
   کافی است با گوشی وصل شوید و `http://192.168.1.1` را باز کنید؛ صفحه به‌محض باز شدن،
   **ساعت و تاریخ گوشی را خودکار می‌فرستد** و RTC ست می‌شود. در همان صفحه:
   - دکمه‌ی همگام‌سازی مجدد
   - ورود دستی تاریخ/ساعت
   - انتخاب حالت کاری: «کار عادی» یا «نمایش دیتا»

3. **ادامه با ساعت فعلی RTC** اگر کسی وصل نشد (تایم‌اوت ۲ دقیقه).

## ۴) باگ‌هایی که همین‌جا رفع شدند

| # | مشکل نسخه‌ی قبل | وضعیت |
|---|---|---|
| ۱ | در حالت «نمایش دیتا» وای‌فای خاموش بود و `debugServer.begin()` روی هیچ شبکه‌ای بالا نمی‌آمد | ✅ حالا AP `RF_TESTER` روی `192.168.1.1` بالا می‌آید |
| ۲ | تسک رله در حالت دیباگ کامنت‌شده بود ولی عملاً می‌چرخید | ✅ در حالت نمایش دیتا واقعاً `vTaskDelete` می‌شود |

## ۵) قبل از فلش

- اگر `TIME_NETWORKS` را خالی بگذارید، مرحله‌ی NTP رد می‌شود و مستقیم پورتال `SetClock` بالا می‌آید.
- برای Production مقدار `DEBUG_MODE` را `0` کنید.
- کامپایل با `esp32:esp32@3.1.1` در ورک‌فلوی `firmware-ci.yml` تأیید می‌شود
  (در این سندباکس امکان کامپایل نبود چون دسترسی به سرورهای Arduino/Espressif بسته است).
