# حالت دیتا، ترتیب رله، و پایداری ران‌تایم (فریمور V2.2)

## ۱) حالت دیتا — «هر وسیله‌ای وصل شد، دیتا برود توی app.py»

تا قبل از این، دو فرمت جدا وجود داشت: مسیر سریال خط `NUM=...` می‌داد و حالت
هات‌اسپات JSON. یعنی گوشی و کامپیوتر دو چیز متفاوت می‌دیدند و خروجی هات‌اسپات
اصلاً به درد `app.py` نمی‌خورد. حالا **یک فرمت واحد** وجود دارد.

### تنها منبع فرمت در فریمور

```cpp
void formatRecordLine(const WifiData &d, char *out, size_t outSize) {
  snprintf(out, outSize,
    "NUM=%d,NBCM1=%s,...,Date=%04d-%02d-%02d,Time=%02d:%02d:%02d", ...);
}
```

هم مسیر آپلود (ESP8266 → سریال → Flask) و هم حالت دیتا از همین یک تابع
استفاده می‌کنند. تست CI چک می‌کند نسخه‌ی دومی از این فرمت در کد نباشد.

### دستورهای حالت دیتا (پاسخ برای همه یکسان)

| دستور | پاسخ |
|---|---|
| `sync` | آخرین رکورد |
| `sync10` | ۱۰ رکورد آخر (قدیم → جدید) |
| `syncall` | کل فایل امروز |
| `info` | `DEVICE=RF_TESTER,FW=2.2,TIME=...,HEAP=...` |

هر پاسخ با یک خط `END` تمام می‌شود. نبودِ داده = `NO_DATA`.

### مسیر داده

```
                    ┌──────── گوشی (اپ اندروید) ────────┐
ESP32 ── TCP ───────┤                                   ├── POST /api/ingest ──► app.py ──► SQLite
  (خط NUM=…)        └──── کامپیوتر (کلاینت دسکتاپ) ─────┘
                                                                   ▲
ESP32 ── TCP ──► ESP8266 ── Serial ────────────────────────────────┘
```

هر سه مسیر عیناً یک رشته را حمل می‌کنند و به یک تابع (`parse_industrial_line`)
و یک کلید یکتایی می‌رسند. پس اگر هم گوشی و هم کامپیوتر همان رکورد را بفرستند،
فقط یک بار ذخیره می‌شود.

### ورودی سرور

```
POST /api/ingest
Content-Type: application/json
{"lines": ["NUM=…", "NUM=…"]}         یا متن خام چندخطی
→ {"saved": 2, "duplicates": 0, "invalid": 0}
```

- در کلاینت دسکتاپ: فیلد «آدرس app.py» + دکمه‌ی **ارسال به app.py**
- در اپ اندروید: همان فیلد و دکمه، با همان خروجی

## ۲) ترتیب رله و مانیتورینگ (دقیقاً چیزی که خواستید)

```cpp
digitalWrite(cfg.relayPin, HIGH);                 // 1) رله فعال
vTaskDelay(pdMS_TO_TICKS(RELAY_SETTLE_MS));       //    پایدار شدن کنتاکت (۵۰ms)
beginFeedbackWindow();                            // 2) مانیتورینگ فعال
vTaskDelay(pdMS_TO_TICKS(FEEDBACK_WINDOW_MS));    // 3) زمان مجاز (۳s)
endFeedbackWindow();                              // 4) مانیتورینگ غیرفعال
digitalWrite(cfg.relayPin, LOW);                  // 5) رله غیرفعال
```

### منطق تکرار (سقف ۳ بار)

| وضعیت بعد از یک تلاش | کار بعدی |
|---|---|
| هم Open و هم Close دیده شد | تمام؛ **هیچ تکراری انجام نمی‌شود** |
| فقط یکی دیده شد | همان که آمده حفظ می‌شود و فقط برای بخشِ نیامده دوباره تلاش می‌شود (+ چکش‌کاری) |
| هیچ‌کدام نیامد | تلاش کامل بعدی |
| بعد از ۳ تلاش | کانال NOK ثبت می‌شود |

نتیجه **تجمعی** است: اگر Open در تلاش ۱ و Close در تلاش ۲ دیده شود، کانال
موفق حساب می‌شود. قبلاً هر تلاش نتیجه‌ی قبلی را پاک می‌کرد و موفقیت فقط وقتی
ثبت می‌شد که هر دو در **یک** تلاش بیایند.

قبلاً مانیتورینگ **قبل از** رله روشن می‌شد و رله هم وسط پنجره خاموش می‌شد؛
به همین دلیل بعضی پالس‌های فیدبک بیرون از پنجره می‌افتادند. حالا کل پنجره
دقیقاً در بازه‌ای است که رله فعال است. بعد از تمام شدن کانال ۱، همین دنباله
برای کانال ۲ اجرا می‌شود. تست CI ترتیب این پنج خط را بررسی می‌کند.

## ۳) تنظیم هسته‌ها برای ران‌تایم دائمی

| تسک | هسته | اولویت | استک | چرا |
|---|---|---|---|---|
| `DigiRead` | 1 | 6 | 4096 | حساس‌ترین بخش زمانی؛ نباید پشت شبکه بماند |
| `RelayCtrl` | 1 | 5 | 6144 | زمان‌بندی پالس‌ها |
| `SHTRead` | 1 | 3 | 4096 | I2C |
| `WiFiConn` | **0** | 2 | 10240 | TCP/SD ممکن است بلاک شود؛ کنار درایور وای‌فای |
| `Health` | 0 | 1 | 3072 | ناظر سلامت |

قبلاً همه روی هسته‌ی ۱ بودند؛ هر بار که TCP بلاک می‌شد، زمان‌بندی رله‌ها
می‌لرزید و در بدترین حالت واچ‌داگ برد را ریست می‌کرد.

### ناظر سلامت (هر ۳۰ ثانیه)

```
[HEALTH] heap=183204 min=170112 | hb R:12 D:48 S:12 N:9412 | up=1440s
```

- حافظه‌ی آزاد و کمینه‌ی تجربه‌شده
- ضربان هر تسک (R=رله، D=دیجیتال، S=سنسور، N=شبکه)
- اگر تسک شبکه یا رله ۵ دقیقه هیچ پیشرفتی نداشته باشد، برد **کنترل‌شده**
  ری‌استارت می‌شود تا دستگاه نیمه‌مرده نماند
- هشدار وقتی heap زیر ۲۰KB برود

> عمداً از `esp_task_wdt` استفاده نشده چون امضای آن بین core 2.x و 3.x فرق
> دارد و کد را غیرقابل‌کامپایل می‌کند؛ این ناظر روی هر دو نسخه کامپایل می‌شود.
